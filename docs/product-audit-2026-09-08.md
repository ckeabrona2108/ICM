# FULL PRODUCT AUDIT — MUSIC DISTRIBUTION SERVICE

Дата аудита: 2026-09-08. Проверка выполнялась на desktop viewport 1440x1000 через локальный dev-сервер `127.0.0.1:3001`, тестовый пользовательский профиль и чтение кода. Опасные действия не выполнялись: релиз не отправлялся на модерацию, платежи и выплаты не проводились, админские решения не применялись.

## Проверенное покрытие

- Авторизация тестового пользователя: вход успешен.
- Desktop flow создания релиза: создание черновика, автосохранение, восстановление из списка черновиков, обязательные поля, загрузка обложки, выбор площадок/стран, загрузка аудио и ошибки файла.
- Кабинет релизов: опубликованные/принятые карточки, черновики, статусы и таймлайн.
- Финансы, аналитика, админка и часть статусов: кодовый аудит плюс локальные unit/in-memory проверки, без реальных выплат и без админского аккаунта.
- Не удалось полностью проверить live: финальный review релиза, отправку на модерацию, платежный checkout, live-аналитику/экспорт и админские экраны. Причина: повторная desktop-сессия упала на ошибке базы `Can't reach database server at localhost:5433`.

## Существенные findings

### P0 — Баланс и выплаты расходятся между legacy и canonical источниками

Где: `src/app/api/finance/payouts/request/route.ts:76`, `src/lib/finance-service.ts:230`, `src/app/api/admin/finance/payouts/[id]/paid/route.ts:46`.

Что происходит: пользовательская заявка создается в `tx.payouts`, но расчет баланса предпочитает `payoutRequest`, если такая таблица есть. В canonical baseline есть обе таблицы. Админский `paid` меняет только `payouts.confirmed = true`, ledger-транзакция списания не создается.

Почему плохо: это финансовый инвариант. При наличии обеих таблиц pending legacy-выплаты могут не резервировать баланс, а после отметки `paid` баланс может снова стать доступным к выводу. Это прямой риск повторной выплаты или ручной сверки денег вне системы.

Как исправить: выбрать один источник выплат, мигрировать данные, читать/писать/админить одну модель, а при `paid` создавать `PAYOUT` transaction в той же транзакции и запрещать повторные переходы.

Тип: подтверждено кодом и in-memory проверкой сервиса.

### P1 — Повторный submit может сломать оплату релиза по подписке

Где: `src/app/api/releases/submit/route.ts:171`, `src/app/api/releases/submit/route.ts:190`, `src/app/api/releases/submit/route.ts:445`, `src/app/api/releases/submit/route.ts:477`.

Что происходит: route проверяет только ownership релиза, заново считает quota и дальше может уйти в `requiresPaymentForNextRelease`. Если первый submit уже подтвердил релиз подпиской, повторный запрос того же `releaseId` может увидеть квоту использованной и записать `confirmed: false` + `payment_required`.

Почему плохо: сетевой ретрай, двойной клик в другой вкладке или восстановленный POST после timeout превращают оплаченный/покрытый подпиской релиз в платный. Пользователь и админ получат противоречивый статус.

Как исправить: сделать submit идемпотентным: если релиз уже отправлен с paymentUsage, возвращать текущий результат; в quota usage исключать текущий releaseId; добавить optimistic version/state guard.

Тип: подтверждено кодом, route-level БД-ретрай не выполнялся.

### P1 — Серверные lifecycle-ограничения редактирования не применяются

Где: `src/app/api/releases/draft/route.ts:202`, `src/app/api/releases/draft/route.ts:241`, `src/app/api/releases/submit/route.ts:301`, `src/lib/release-policy.ts:986`.

Что происходит: policy запрещает редактировать релиз на модерации, но PATCH черновика обновляет любой owned release и сохраняет текущий status/confirmed. Edit-submit тоже не вызывает `canEditRelease`.

Почему плохо: UI может скрывать действие, но старая открытая вкладка или прямой API сохранят новые roles/title/tracks после отправки на модерацию.

Как исправить: на сервере блокировать PATCH/edit-submit для `moderation`, `approved`, `archived` без явного разрешенного flow; для approved использовать отдельную сущность версии.

Тип: подтверждено кодом.

### P1 — Договор/верификация защищают UI, но не submit route

Где: `src/app/api/releases/submit/route.ts:112`, `src/app/(dashboard)/dashboard/layout.tsx:162`, `src/components/layout/dashboard-sidebar.tsx:528`.

Что происходит: layout/sidebar ограничивают создание по `getUserContractStatus`, но `/api/releases/submit` не делает повторную проверку. В wizard при ошибке проверки статуса есть fail-open сценарий.

Почему плохо: договор и KYC являются gating-условием перед выпуском. Такой gate должен быть серверным, иначе его можно обойти прямым запросом или stale-сессией.

Как исправить: вызывать `getUserContractStatus` внутри submit route, возвращать 403 с понятной причиной, покрыть тестом прямого API.

Тип: подтверждено кодом, обычный вход через UI частично защищен.

### P1 — Сервер может принять релиз без загруженного аудиофайла

Где: `src/lib/release-policy.ts:84`, `src/lib/release-policy.ts:688`, `src/lib/release-policy.ts:906`, `src/lib/release-submit-tracks.ts:42`.

Что происходит: `audioFile` optional. Валидация требует duration, но не требует сохраненный файл. Submit tracks сохраняет `audioFile: null`, если поле отсутствует.

Почему плохо: прямой API может создать модерационный релиз с названием файла, duration и `hasAudio`, но без объекта в storage. Модератор и downstream delivery получат неполный релиз.

Как исправить: для всех треков, которые идут на streaming platforms, требовать валидный uploadedFile с storageKey/url и проверять статус upload на сервере.

Тип: подтверждено кодом; live UI с валидным wizard без файла это не пропускает.

### P1 — Relink аналитики теряет платформу и может затирать streams

Где: `src/lib/analytics-import-service.ts:700`, `src/lib/analytics-import-service.ts:1232`, `src/lib/analytics-import-service.ts:1368`, `src/lib/analytics-import-service.ts:1391`, `src/lib/analytics-import-service.ts:1393`, `src/lib/analytics-import-service.ts:298`.

Что происходит: import группирует строки с учетом platform, но unmatched payload platform не сохраняет. При relink система записывает `period_days: 30`, `platform: "Unknown"`. В обычном upsert path update пишет `streams: row.streams`, а не increment.

Почему плохо: после ручной привязки две платформы на один UPC/date/country могут схлопнуться в одну запись `Unknown`, а последняя запись перезапишет предыдущие streams. Отчеты станут недостоверными.

Как исправить: хранить platform в unmatched, relink переносить оригинальную platform/period, upsert делать additively или ввести уникальный import id + дедупликацию.

Тип: подтверждено кодом и in-memory сценарием.

### P1 — Обязательные банковские реквизиты теряются после отправки заявки

Где: `src/lib/finance-policy.ts:131`, `src/lib/finance-policy.ts:140`, `src/app/api/finance/payouts/request/route.ts:76`, `src/lib/admin-payouts-service.ts:42`.

Что происходит: policy требует `bankName` и `taxId`, но route сохраняет только `recieverName`, `accountNumber`, `amount`, `confirmed`. Admin mapper ожидает `bankName/taxId`, но legacy payout их не содержит.

Почему плохо: админ видит заявку без обязательных реквизитов и вынужден сверять вручную или запрашивать данные повторно.

Как исправить: расширить модель payout или перейти на `payoutRequest`, сохранять все поля из schema, показать их в админке и audit-log.

Тип: подтверждено кодом.

### P1 — Редактирование принятого релиза может застрять из-за UPC

Где: `src/lib/map-cabinet-to-wizard-seed.ts:164`, `src/lib/admin-release-service.ts:178`, `src/lib/admin-release-service.ts:183`.

Что происходит: копия для редактирования принятого релиза сохраняет исходный UPC, но approve проверяет любой другой release с тем же UPC и возвращает `UPC_ALREADY_EXISTS`.

Почему плохо: нормальный flow правки принятого релиза может создать новую версию, которую нельзя одобрить без ручного изменения UPC, хотя для музыкального релиза UPC должен оставаться тем же при корректной версии/замене.

Как исправить: добавить relation `sourceReleaseId/replacesReleaseId`, при approve разрешать тот же UPC внутри version-chain и явно закрывать старую версию.

Тип: высокая уверенность по коду; live approve не выполнялся.

### P2 — UI сообщает `Опубликован` после внутреннего approve

Где: `src/lib/release-timeline-state.ts:112`, live desktop карточки принятых релизов JIJO и NOT AFRAID.

Что происходит: `approved`, `distributed`, `archived` мапятся в step `published`. В UI принятый релиз показывает финальный таймлайн `Опубликован`.

Почему плохо: для дистрибуции музыки `approved` не равно `live на площадках`. Пользователь может ожидать, что Spotify/Apple/Yandex уже обновлены.

Как исправить: разделить статусы `approved`, `delivered`, `live`, `failed`, `partial_live`; показывать DSP receipt/date per platform.

Тип: подтверждено кодом и live desktop карточками.

### P2 — Админская очередь плохо масштабируется и использует неверные даты

Где: `src/lib/admin-release-queries.ts:145`, `src/lib/admin-release-queries.ts:196`, `src/lib/admin-release-queries.ts:302`.

Что происходит: `getAdminReleases` загружает все релизы с треками, фильтрует в памяти и сортирует по release date. `submittedAt/approvedAt/rejectedAt` формируются из `source.date`, а не из фактической даты действия.

Почему плохо: очередь модерации не отражает SLA и будет тяжелой на большом каталоге.

Как исправить: хранить реальные timestamps, фильтровать/пагинировать в SQL, сортировать по submittedAt/priority.

Тип: подтверждено кодом.

### P2 — Desktop wizard перегружен и сбрасывает контекст шага

Где: live desktop flow создания релиза.

Что происходит: при повторном открытии сохраненного черновика данные восстановились, но wizard вернулся к intro/первому шагу. На desktop экран занимает большой внешний заголовок, внутренний заголовок карточки, предупреждение и step header, из-за чего рабочие поля уходят ниже первого экрана.

Почему плохо: пользователь после перерыва не понимает, где он остановился. Для частого операционного сценария это лишние клики и риск пропустить ошибку.

Как исправить: сохранять последний шаг в draft persistence, убрать дублирующие заголовки, сделать stepper с названиями шагов вместо `Шаг 1/2/...`.

Тип: подтверждено live desktop.

### P2 — Загрузка плохого аудиофайла дает позднюю ошибку

Где: live desktop flow, шаг `Загрузка аудио`.

Что происходит: файл `invalid-audio.wav` попал в список загруженных треков и показал metadata-панель; только при переходе дальше появилась ошибка `Не удалось определить длительность...`.

Почему плохо: пользователь получает ложное ощущение, что файл принят. Чем позже ошибка, тем больше потерянного ввода вокруг метаданных.

Как исправить: после upload/metadata probe сразу показывать fail-state на карточке файла и не считать его загруженным треком до успешного определения duration/codec.

Тип: подтверждено live desktop.

### P2 — Статус `Сервис не работает` описывает расписание поддержки, а не работоспособность кабинета

Где: `src/lib/service-status.ts:55`, `src/lib/service-status.ts:69`, live шапка кабинета.

Что происходит: шапка пишет `Сервис работает` или `Сервис не работает` по расписанию. При этом кабинет фактически остается доступен.

Почему плохо: для музыкального дистрибьютора это читается как outage продукта, особенно рядом с созданием релиза и финансами.

Как исправить: переименовать в `Поддержка онлайн/офлайн` или `Операторы отвечают до ...`, отдельно мониторить реальную доступность API.

Тип: подтверждено кодом и live desktop.

### P2 — Сбои данных в dashboard layout маскируются нулями

Где: `src/app/(dashboard)/dashboard/layout.tsx:98`, `src/app/(dashboard)/dashboard/layout.tsx:126`, `src/app/(dashboard)/dashboard/layout.tsx:189`.

Что происходит: ошибки баланса, подписки и AI tokens ловятся и заменяются fallback-значениями.

Почему плохо: если БД/сервис недоступны, пользователь может увидеть `0,00 ₽` или отсутствие подписки вместо ошибки загрузки. Для финансов это плохой UX и риск поддержки.

Как исправить: показывать explicit degraded state: `Не удалось загрузить баланс`, disable payout/payment actions до успешной загрузки.

Тип: подтверждено кодом; live повторная проверка упала из-за базы.

### P2 — Сброс пароля удаляет database sessions, но auth работает на JWT

Где: `src/app/api/auth/reset-password/route.ts:61`, `src/lib/auth.ts:104`, `src/lib/auth.ts:145`.

Что происходит: reset-password обновляет пароль и удаляет записи `sessions`, но NextAuth настроен на `strategy: "jwt"` с maxAge 30 дней; session callback берет роль/id из токена.

Почему плохо: старые JWT могут оставаться валидными после смены пароля. Для админов это особенно чувствительно.

Как исправить: добавить `tokenVersion/passwordChangedAt` в JWT/session callback и сравнивать с БД, либо перейти на server-side sessions.

Тип: подтверждено кодом; live security test не выполнялся.

## Major Improvements

## Hidden Risks

- Локальный запуск нестабилен: `localhost:3000` отдавал 404 по CSS/JS, отдельный dev-сервер позже потерял базу `localhost:5433`.
- UI иногда показывает разные признаки верификации пользователя; нужна отдельная проверка источников `getUserContractStatus` и user profile badge.
- Tests в нескольких местах проверяют helpers или устаревшие mocks, а не production routes. Это снижает шанс поймать regressions в submit/admin import flows.
- Прямые API-route сценарии опаснее, чем UI: часть ограничений есть только в компонентах.
- Админские `processing/paid/reject` выплаты не выглядят как строгая state machine с неизменяемым audit ledger.

## Admin Risks

- Approve route и decision route расходятся по требованиям UPC: один требует UPC, другой может принять `upc ?? release.upc`.
- Queue грузит все релизы с треками и фильтрует в памяти, поэтому при росте каталога начнутся latency/timeout проблемы.
- Даты в очереди берутся из даты релиза, а не из submitted/approved/rejected timestamps.
- Ручной relink аналитики может менять UPC релиза при несовпадении с импортированной строкой.
- Нет live-проверки под админом: выводы по админке основаны на коде и unit/in-memory сценариях.

## Release Flow Verdict

Вердикт: выпуск релиза usable для простого черновика, но пока не готов как надежный production release pipeline.

Три главных риска:

1. Повторная отправка может изменить оплату/квоту уже отправленного релиза.
2. Сервер принимает состояния, которые UI пытается запретить: lifecycle edit, договор, audio storage.
3. Статус `approved` показывается пользователю как `published`, хотя фактическая доставка на площадки в проверенном коде не подтверждена.

## Analytics / Reporting Trust Verdict

Вердикт: финансовым и аналитическим отчетам нельзя полностью доверять без сверки.

Причины: payout reserve/debit расходится между таблицами, обязательные реквизиты выплат теряются, unmatched analytics relink теряет platform и может затирать streams. До исправления этих мест отчеты лучше считать operational dashboard, а не source of truth.
